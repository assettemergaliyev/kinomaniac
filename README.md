# Киноманьяк — AI Movie Recommendation System

Учебный проект по AI Engineering: система рекомендаций фильмов на основе локальной Large Language Model (LLM).

## О проекте

«Киноманьяк» принимает текстовый запрос пользователя на естественном языке и рекомендует от 1 до 3 фильмов из заранее подготовленного каталога `films.json`.

Для генерации рекомендаций используется локальная модель `qwen3.5:4b` через Ollama и OpenAI-совместимый API.

**Основные возможности:**
- Поиск фильмов по текстовому запросу на русском и казахском языках.
- Рекомендации только из локального каталога.
- Структурированные ответы с использованием Pydantic.
- Проверка существования `film_id` и отсутствия дубликатов.
- Обработка ситуации, когда подходящих фильмов нет (`no_match`).
- Журналирование запросов и результатов в `calls.jsonl`.
- Автоматические тесты с использованием pytest.

## Технологии

- Python 3.12
- Ollama
- Qwen 3.5 (`qwen3.5:4b`)
- OpenAI Python SDK
- Pydantic
- pytest
- uv

## Каталог фильмов

Каталог `films.json` содержит 50 фильмов, включая 10 казахстанских.

Для каждого фильма указаны идентификатор, название, год выпуска, продолжительность, жанры, страны, языки и краткое описание.

## Установка и запуск

### Требования

Для запуска проекта необходимы:

- Python 3.12
- uv — менеджер зависимостей Python
- Ollama — для локального запуска LLM
- Модель `qwen3.5:4b`

### 1. Установка зависимостей

Находясь в корневой папке проекта, выполните:

```powershell
uv sync --frozen
```

Команда устанавливает зависимости из `uv.lock` без обновления lock-файла.

### 2. Подготовка Ollama

Установите Ollama и загрузите модель:

```powershell
ollama pull qwen3.5:4b
```

Убедитесь, что Ollama запущена и её API доступен по адресу `http://localhost:11434`.

### 3. Запуск рекомендаций

Передайте текстовый запрос в качестве аргумента:

```powershell
uv run kino.py "Посоветуй фантастический фильм про космос"
```

Программа выведет до трёх рекомендаций с названием, годом, продолжительностью, описанием и объяснением выбора.

Если подходящих фильмов нет, программа вернёт результат `no_match`.

### 4. Проверка тестовых запросов

```powershell
uv run check.py
```

Команда последовательно отправляет запросы из `queries.json` локальной модели.

### 5. Просмотр статистики

```powershell
uv run show.py
```

Команда выводит статистику результатов из журнала `calls.jsonl`.

### 6. Автоматические тесты

```powershell
uv run pytest -q
```

Тесты проверяют корректность бизнес-валидации без обращения к Ollama.

## Ограничения системы

Проект использует локальную языковую модель `qwen3.5:4b` через Ollama.

**Известные ограничения:**

- **Нестабильность структурированных ответов.** Модель иногда возвращает `status="no_match"` с непустым `picks`. Такие ответы отклоняются Pydantic-валидатором и получают исход `invalid`.
- **Ошибки в объяснениях.** Даже при правильном статусе модель может неверно описывать характеристики фильмов или содержимое каталога.
- **Качество рекомендаций.** Наличие корректного `film_id` не гарантирует, что фильм действительно соответствует всем смысловым ограничениям запроса.
- **Ограниченный каталог.** Система рекомендует только фильмы из `films.json`. Отсутствие совпадений означает отсутствие подходящего фильма в каталоге, а не среди всех существующих фильмов.
- **Отсутствие автоматического повторного запроса.** При ошибке валидации программа возвращает `invalid`, не пытаясь повторно обратиться к модели.

Для снижения рисков программа проверяет ID, количество рекомендаций, отсутствие повторов и соответствие структуры ответа схеме Pydantic. Фактические сведения о фильмах выводятся из каталога, а не из памяти LLM.

## Ответы на вопросы задания

### 1. Почему программа сверяет ID, а не название фильма?

Название фильма ненадёжно как идентификатор: оно может иметь разные переводы, варианты написания или совпадать с названием другого фильма.

Поэтому LLM возвращает `film_id`, а программа проверяет его наличие в каталоге (`kino.py`, строки 89–91). После проверки фильм находится по ID, а его название и характеристики берутся непосредственно из `films.json` (`kino.py`, строки 195–199).

Это позволяет не доверять фактические характеристики фильма памяти языковой модели.

**Результат эксперимента:** при запросе года выпуска и продолжительности 10 фильмов без каталога модель `qwen3.5:4b` допустила хотя бы одно расхождение для **8 из 10 фильмов**. Полностью совпали оба параметра только у двух фильмов.

Эксперимент реализован в `experiment.py`, результаты приведены выше в разделе «Эксперимент: проверка фактических знаний LLM».

### 2. Что произойдёт, если модель вернёт чужой film_id?

Программа не покажет пользователю фильм, которого нет в каталоге.

Функция `validate_picks()` формирует множество допустимых ID и проверяет каждый ID, возвращённый моделью (`kino.py`, строки 89–103).

Если обнаружен чужой ID, функция `pick()` собирает такие значения в список `rejected` и возвращает `("invalid", [])` (`kino.py`, строки 179–189). Пустой список означает, что пользователю не будет показана ни одна рекомендация из некорректного ответа.

Через функцию `finish()` результат записывается в `calls.jsonl`: `outcome="invalid"`, `ids=[]`, а отклонённые ID сохраняются в поле `rejected` (`kino.py`, строки 111–138).

Таким образом, даже если модель сгенерирует несуществующий ID, проверка в Python не позволит вывести соответствующий фильм.

### 3. Чем успешный ответ модели отличается от правильной рекомендации?

`outcome="ok"` означает, что модель вернула структурированный ответ, который прошёл проверки программы: ID существуют в каталоге, не повторяются, а количество рекомендаций допустимо (`kino.py`, строки 89–108).

Но технически корректный ответ не обязательно является хорошей рекомендацией. Модель может выбрать существующий фильм, который не соответствует смыслу запроса.

В `check.py` эти критерии разделены:

- Строки 42–43 учитывают технический исход каждого вызова.
- Строки 45–53 проверяют, присутствует ли хотя бы один ожидаемый ID из `must` в успешном ответе.
- Строки 58–79 выводят статистику исходов и количество пройденных проверок `must`.

Например, если модель вернула `outcome="ok"`, но не выбрала ни одного фильма из `must`, технический вызов считается успешным, а проверка ожидаемой рекомендации — непройденной.

**Ограничение:** проверка `must` не гарантирует полного соответствия всем условиям запроса. Для этого потребовались бы дополнительные проверки, например фильтрация по продолжительности, языку и жанру.

### 4. Как можно решить задачу без ML и чего не хватает такому решению?

Без ML можно реализовать поиск фильмов с помощью обычных правил и фильтров Python: по году выпуска, продолжительности, жанру, стране и языку.

Например, запросы из `queries.json` о фильме 1895 года, продолжительности ровно 999 минут или длительности меньше 120 минут можно обработать сравнением значений с полями `year` и `minutes` из `films.json`.

Однако такого решения недостаточно для сложных запросов:

- «Фантастический фильм, где герой снова и снова переживает один день» — необходимо понимать смысл описания фильма, а не только его жанр.
- «Фантастический фильм, но не про космос» — нужно учитывать отрицание и тематику фильма.
- «Драматический фильм с неожиданной концовкой» — требуется интерпретация сюжетных характеристик, которые могут отсутствовать в структурированных полях.

Для обработки таких запросов без ML пришлось бы вручную создавать дополнительные признаки, словари синонимов и правила интерпретации текста.

В текущем проекте LLM интерпретирует запрос и выбирает фильмы из переданного каталога (`kino.py`, строки 130–147), а Python проверяет допустимость выбранных ID (`kino.py`, строки 89–108).

При этом LLM не гарантирует соблюдение всех смысловых ограничений: проверка ID защищает от несуществующих фильмов, но не от неподходящих рекомендаций.

### 5. Сколько стоит один запрос и что влияет на цену?

Проект использует локальную модель `qwen3.5:4b` через Ollama, поэтому стоимость облачного API составляет **$0 за запрос**. При этом локальный запуск потребляет вычислительные ресурсы компьютера и электроэнергию.

В одном измеренном запросе «Посоветуй фантастический фильм про космос» модель использовала:

- Входные токены (`prompt_tokens`): **2050**
- Выходные токены (`completion_tokens`): **98**
- Всего (`total_tokens`): **2148**

Основную часть токенов составляет входной контекст, поскольку программа передаёт модели весь каталог из 50 фильмов (`kino.py`, строки 142–147).

При использовании облачной модели стоимость зависела бы от тарифов провайдера и количества входных и выходных токенов. На расход токенов особенно влияют размер каталога, длина инструкций и объём ответа модели.

Программа сохраняет доступную статистику токенов в `calls.jsonl` (`kino.py`, функция `pick()`), а `show.py` суммирует её и показывает стоимость API для известных локальных моделей.

**Ограничение измерения:** на момент проверки журнал содержал 45 вызовов, но данные о токенах были доступны только для одного. Поэтому 2148 токенов — результат конкретного запроса, а не среднее значение по всем вызовам.

## Пять вопросов лекции 1

### 1. Какова цель задачи?

Создать программу, которая подбирает от одного до трёх фильмов по запросу пользователя на естественном языке, используя каталог `films.json`.

Программа должна учитывать пожелания пользователя и не рекомендовать фильмы, отсутствующие в каталоге.

Основной критерий успешности — не просто получение корректного ответа от LLM, а подбор подходящих фильмов с проверкой их идентификаторов.

Реализация: `kino.py`, функция `pick()`. Проверка ожидаемых рекомендаций: `check.py`, строки 45–53.

### 2. Как решить задачу без ML?

Без ML можно реализовать рекомендательную систему на основе заранее заданных правил (Software 1.0).

Программа анализирует запрос пользователя, определяет условия поиска и фильтрует `films.json` по структурированным полям: жанру, году выпуска, продолжительности, стране и языку.

Например, для запроса «фильм длительностью меньше 120 минут» достаточно проверить условие `minutes < 120` для каждой записи каталога.

Такое решение можно использовать как baseline для сравнения с LLM.

**Ограничение:** сложные запросы, например «фантастический фильм, но не про космос», требуют интерпретации смысла и отрицаний. Для их обработки без ML понадобятся дополнительные правила, словари и признаки.

В текущей реализации интерпретацию естественного языка выполняет LLM (`kino.py`, функция `pick()`), а проверку допустимости рекомендаций — Python (`kino.py`, строки 89–108).

### 3. Какие данные используются?

Программа использует два основных источника данных:

1. **Каталог `films.json`** — 50 фильмов с уникальными идентификаторами `id`, названиями `title`, годами выпуска `year`, продолжительностью `minutes`, жанрами `genres`, странами `countries`, языками `languages` и описаниями `description`.
2. **Запрос пользователя** — текст на естественном языке, содержащий пожелания к фильму, например жанр, тематику, продолжительность или исключения.

Каталог передаётся готовой LLM вместе с запросом. Модель анализирует их и предлагает идентификаторы подходящих фильмов.

Дополнительно используются:

- `queries.json` — 15 тестовых запросов для проверки поведения программы.
- `calls.jsonl` — журнал вызовов модели, результатов проверки и доступной статистики токенов.

**Важно:** каталог не является обучающей выборкой для дообучения модели. В проекте используется **inference** — применение уже обученной LLM.

Реализация: `kino.py`, функции `build_messages()` и `pick()`; проверка запросов: `check.py`.

### 4. Что выдаёт программа?

Программа возвращает результат подбора фильмов по запросу пользователя.

При успешном подборе (`status = "ok"`) она показывает от одного до трёх фильмов из каталога. Для каждого фильма выводятся:

- Название и год выпуска.
- Продолжительность в минутах.
- Описание из `films.json`.
- Объяснение от LLM, почему фильм соответствует запросу.

Модель возвращает структурированный ответ с идентификаторами `film_id` и объяснениями `why`. Python проверяет идентификаторы и берёт фактические сведения о фильмах из каталога, а не из ответа модели.

Если подходящих фильмов нет (`status = "no_match"`), программа выводит причину без рекомендаций.

Если модель возвращает недопустимые идентификаторы, дубликаты или неправильное количество рекомендаций, результат отклоняется как `invalid`.

Реализация: `kino.py`, модели `Recommendation` и `FilmPick`, функции `validate_picks()` и `pick()`.

### 5. Какова цена ошибки?

Основная цена ошибки в рекомендательной системе — неудовлетворённость пользователя и снижение доверия к рекомендациям.

Можно выделить два типа ошибок:

- **False Positive (FP)** — программа рекомендует фильм, который не соответствует запросу. Например, предлагает фильм про космос, хотя пользователь явно попросил фильм не про космос.
- **False Negative (FN)** — программа не рекомендует подходящий фильм, хотя он присутствует в каталоге.

Для этого учебного проекта более заметной ошибкой считаю FP: пользователь получает неподходящую рекомендацию и может потратить время на её просмотр. Однако относительная стоимость FP и FN — предположение, а не результат измерения.

Отдельный риск — рекомендация несуществующего фильма или фильма вне каталога. Для снижения этого риска программа проверяет `film_id` и отклоняет недопустимые ответы (`kino.py`, функция `validate_picks()`).

`check.py` проверяет результаты на 15 тестовых запросах и отдельно учитывает выполнение условий `must`. Однако эта проверка не измеряет полноценные Precision и Recall, поэтому реальную частоту FP и FN по её результатам определить нельзя.
